# Контракт JWT

Единственный общий контракт между сервисами: формат токена, который выпускает
service-auth и проверяют остальные сервисы.

## Алгоритм и claims

- Алгоритм: **RS256** (асимметричный — service-auth подписывает приватным
  ключом, остальные сервисы проверяют публичным).
- `iss` = `service-auth`
- `aud` = `internal`
- `sub` — `user_id`
- `company_id` — юрлицо, от имени которого работает пользователь; все
  доменные данные в service-core разделены по этому полю
- `iat` — время выпуска
- `exp` — **обязателен**. Токен без `exp` считается невалидным и отклоняется
  при проверке (иначе он никогда не истекает). TTL по умолчанию — 7 дней.

## Кто выпускает и кто проверяет

- **Выпускает** только service-auth, приватным ключом
  (`JWT_PRIVATE_KEY_PATH`), в `/api/auth/register` и `/api/auth/login`.
- **Проверяет** service-core и service-commission, публичным ключом
  (`JWT_PUBLIC_KEY_PATH`), полностью локально — без обращения к service-auth
  по сети на каждый запрос.

## Известная асимметрия

Python-зависимость `require_user` в service-commission (план 01) проверяет
только `sub` и пока не использует `company_id` — данные commission ещё не
разделены по юрлицу. Это осознанный технический долг, а не баг: подтягивать
company_id туда — отдельная задача.

## Ротация ключей

Ключи генерируются `infra/gen-keys.sh`. После ротации **все** ранее
выпущенные токены становятся невалидными (подпись проверяется новым
публичным ключом) — пользователям потребуется перелогиниться.
