# 0006. Два периметра: Traefik снаружи, NetworkPolicy внутри

- Статус: принято (план 08, Task 1)
- Дата: 2026-09-21
- Спека: `docs/superpowers/specs/2026-09-15-cbdc-hub-integration-design.md` §3, §8

## Контекст

До плана 08 наружу торчали все сервисы. В compose Traefik держал роутеры
`/api/auth` → service-auth и `/api/core` → service-core рядом с роутером
BFF, то есть SPA могла бы (а внешний клиент — точно мог) ходить в auth и
core мимо BFF. В k3s было хуже: `NetworkPolicy` чарта пускала к сервису
весь namespace `backend`, что при namespace из пяти подов не ограничивает
ничего.

При этом по спеке (§3) BFF — единственная точка входа для SPA, а
единственное разрешённое обращение сервиса к сервису — `service-core` →
`service-commission` за котировкой при подтверждении сценария.

## Решение

Периметра два, и они отвечают за разные вопросы.

**Внешний — Traefik: «кого видно снаружи».** Наружу публикуются только
`frontend` (`PathPrefix(/)`, priority 1) и `bff` (`PathPrefix(/api) ||
PathPrefix(/ws)`, priority 100). Приоритеты заданы явно, а не оставлены на
умолчание «по длине правила»: любое сокращение правила BFF молча отдало бы
`/api` фронту. У auth, core и commission `ingress.enabled: false` — в
чарте нет ни IngressRoute, ни CORS-middleware.

**Внутренний — NetworkPolicy: «кто до кого дотянется внутри».** К auth и
core ходит только под `bff`; к commission — `bff` и `service-core`.
Источники перечислены в `networkPolicy.allowFrom` каждого values, а не
заданы namespace-селектором.

**Почему core разрешено ходить в commission.** Это не исключение «на всякий
случай», а единственное межсервисное обращение, которое есть в домене:
core при подтверждении сценария запрашивает у commission котировку
(`services/service-core/src/commission_client.cc`). Если бы правило
описывалось как «внутри namespace всем можно», оно покрыло бы и этот
вызов, и любой будущий, который никто не проектировал. Явный список
делает появление шестого разрешения видимой правкой в ревью.

## Почему два, а не один

Traefik отвечает на вопрос «что опубликовано», NetworkPolicy — «что
достижимо». Один без другого дырявый в обе стороны:

- только Traefik — любой под в кластере (скомпрометированный sidecar,
  чужой Job, отладочный `kubectl run`) ходит в auth напрямую, минуя BFF с
  его проверкой сессии;
- только NetworkPolicy — сервисы недостижимы изнутри, но их IngressRoute
  по-прежнему публикует их наружу.

## Последствия

- **Периметр нельзя выкатывать по частям.** Пока в кластере нет пода `bff`,
  политика закрывает auth и core для всех, и это выглядит как «сервисы не
  поднялись». Записано в README и в комментариях values.
- **У `bff` и `frontend` NetworkPolicy выключена, и это незакрытый пункт, а
  не «периметр держится на Traefik».** К ним ходит Traefik — под из другого
  namespace (в k3s `kube-system`), чьи метки без живого кластера
  неизвестны, а неверный `podSelector` здесь закрыл бы единственный вход в
  систему. Следствие называется прямо: сейчас к `bff:4000` может ходить
  любой под кластера в обход Traefik и его middleware. Закрывается при
  первом выкате, по фактическим меткам пода Traefik.
- Внутренняя ручка эмулятора `POST /internal/emulator/tick` (спека §4.3) в
  кластере не публикуется вообще; e2e дёргают её только на compose-стенде
  через host-порт 18081 из `docker-compose.dev.yml`.
- Смоук-цели Makefile (`k3s-test-auth`, `k3s-test-core`) ходят через BFF и
  пользуются cookie-сессией: прямых адресов сервисов снаружи больше нет.

## Отвергнутые варианты

- **Оставить прямые роутеры `/api/auth` и `/api/core` «для отладки».** Путь,
  который существует для отладки, существует и для всех остальных; а
  отладка одинаково хорошо делается через `kubectl port-forward`, который
  требует доступа к кластеру.
- **NetworkPolicy по `namespaceSelector: backend`.** Ровно то, что было:
  namespace из пяти подов — это не граница.
- **Разрешить `kube-system` целиком, чтобы закрыть bff сейчас.** Пустило бы
  к сервисам заодно CoreDNS, metrics-server и всё, что там появится позже.
