# 0007. Secret только в k3s, в compose пароли остаются открытыми

- Статус: принято (план 08, Task 2 и Task 3)
- Дата: 2026-09-21
- Спека: `docs/superpowers/specs/2026-09-15-cbdc-hub-integration-design.md` §8

## Контекст

Пароли БД лежали открытым текстом в `infra/helm/values-service-*.yaml`,
то есть в git. В compose они лежат открытым текстом в
`docker-compose.yml` — там же.

## Решение

Разделить два окружения и сказать об этом вслух.

**k3s.** Пароли уезжают в `Secret` релиза. В values остаётся только факт
«у этого релиза есть Secret» (`secrets.enabled: true`) и имя ключа
(`dbPassword: ""`), значения приезжают снаружи git — `--set
secrets.data.dbPassword=...` из CD или файлом, который не коммитится.
Ключ объявлен пустым, а не отсутствует: имя видно в файле (на него
ссылаются `config.json` и `migrations.db.passwordSecretKey`), а забытый
`--set` роняет рендер сообщением про пустое значение.

**compose.** Пароли (`auth`/`core`/`commission`) остаются открытыми.
Compose — локальный стенд: поднимается одной командой на машине
разработчика, ходит по http, не хранит ничего ценного и наружу не
публикуется. Секрет-менеджер для него — плата сложностью за защиту от
несуществующей угрозы. **Compose от этого не стал защищённым, он им и не
был** — и именно это должно быть написано, а не подразумеваться.

## Что из этого следует, и почему сделано именно так

- **`secrets.data` — сырые данные, `secrets.derived` — шаблоны.** Пароль
  пользователя нельзя прогонять через `tpl`: пароль с `{{` внутри уронил бы
  рендер, а валидный шаблон подставился бы молча и по-разному в Secret и в
  `config.json` — сервис и миграции ушли бы в базу с разными паролями.
  Шаблонизируется только то, что написано в репозитории.
- **Гварды намеренно fail-closed.** Рендер падает, если ключа секрета нет,
  если имя ключа непригодно для Kubernetes, если имя переменной окружения
  не C_IDENTIFIER, или если пароль содержит символы, требующие
  процент-кодирования в userinfo URL. Альтернатива — тихо подставленный
  пустой или битый пароль, который доживает до кластера и выглядит как
  `CreateContainerConfigError` или «БД отказывает через раз».
- **Это проверка, а не кодирование.** Процент-энкодер в Helm-шаблоне —
  лекарство хуже болезни: `urlquery` кодирует пробел как `+`, который в
  userinfo раскодируется обратно плюсом, то есть молча меняет пароль.
  Пароли для стенда генерируем мы сами, ограничение набора ничего не стоит.
- **Следствие для генератора паролей:** `openssl rand -base64` выдаёт `/` и
  отвергается собственным гвардом. README и `make k3s-secrets` генерируют
  пароль из `[A-Za-z0-9]`.
- **Пароль задаётся в двух местах, и они связаны одним файлом.** Чарт не
  знает, какой пароль реально у Postgres: его ставит отдельная команда
  (`make k3s-deploy-data`, чарт bitnami). Раньше там стояли литералы
  `auth`/`core`/`commission`, и расхождение давало идеальный рендер и
  `password authentication failed` в поде. Теперь обе команды читают один
  `infra/helm/secrets-k3s.env` (вне git), а в CD — одни и те же
  `secrets.DB_PASSWORD_*`.
- **Ротация пароля — отдельная процедура, а не повторный upgrade.** Чарт
  bitnami/postgresql задаёт пароль только при первой инициализации PVC:
  upgrade с другим `auth.password` оставит в базе старый пароль, а Secret
  сервиса поедет с новым. Менять пароль после первого выката = `ALTER USER`
  в базе или снос PVC.

## Отвергнутые варианты

- **Вынести из DSN только пароль у service-commission.** Пароль там — часть
  строки подключения; собирать DSN внутри сервиса значит править код
  сервиса ради инфраструктурного решения. Поэтому в Secret уезжает весь
  DSN, но передаётся снаружи по-прежнему ОДИН `--set`: DSN выводится в
  `secrets.derived` из `dbPassword`. Два независимых `--set` с одним
  паролем внутри разъехались бы при первой ротации молча.
- **`config.json` в ConfigMap, пароль отдельным Secret.** У auth и core
  пароль лежит внутри `config.json` (`db_clients[].passwd`). Выносить его в
  Secret бессмысленно, если он же рядом в ConfigMap, который отдаётся
  любому с `get configmaps`. Поэтому `config.secret: true`.
- **Секрет-менеджер и для compose.** См. выше: цена без выгоды.
