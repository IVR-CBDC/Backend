# Backend: общий базовый образ, надёжные миграции, CI — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Сделать бэкенд пригодным к автоматической проверке: один базовый образ C++ вместо двух копий сборки drogon, миграции, безопасные при параллельном запуске, честные healthcheck'и в compose и CI, который гоняет все три набора тестов на каждый PR.

**Architecture:** Тяжёлая часть сборки (libjwt + drogon из исходников, ~15 минут) выносится в отдельный образ `ivr-cpp-base`, который собирается только при изменении своего Dockerfile и переиспользуется обоими сервисами — без этого CI на каждый PR собирал бы drogon дважды. `infra/migrate.sh` становится единственным источником правды: helm-чарт перестаёт держать свою копию скрипта, а сам скрипт берёт advisory-lock и записывает факт применения миграции в той же транзакции, что и саму миграцию. CI повторяет то, что разработчик делает локально: `make test-cpp`, тесты commission и `tests/api` против поднятого compose.

**Tech Stack:** Docker (buildx, GitHub Actions cache), Docker Compose, GitHub Actions, ghcr.io, bash/shellcheck, CMake/Catch2, pytest, Helm.

**Spec:** `docs/superpowers/specs/2026-09-15-cbdc-hub-integration-design.md` (§8 «CI Backend», §12 риск «Сборка C++ в CI долгая»), плюс перенесённые пункты из `docs/superpowers/plans/2026-09-15-00-roadmap.md` («04 (compose/CI)»).

**Вне границ (ruling):** роутинг Traefik «наружу только bff и frontend» (спека §3) в этом плане **не делается** — оба сервиса появятся в плане 05, и правка сейчас указывала бы на несуществующие контейнеры. Переносится в план 08 вместе с NetworkPolicy и Secrets.

### Task 2: Надёжные миграции и один источник правды

**Files:**

- Produces: `infra/migrate.sh`, безопасный при параллельном запуске; `infra/gen-migration-values.sh` кладёт в values ключ `migrations.script` (содержимое `infra/migrate.sh`); чарт рендерит скрипт из values, своей копии не держит.

- [ ] **Step 1: Упрочить `infra/migrate.sh`**

Две проблемы: (1) `psql -1 -f "$file"` и следующий за ним `INSERT INTO schema_migrations` — разные транзакции, поэтому падение между ними приводит к повторному применению миграции; (2) две реплики init-контейнера могут применять миграции одновременно.

Исправить:
- В начале работы (после создания `schema_migrations`) взять сессионную блокировку и держать её до конца: `SELECT pg_advisory_lock(hashtext('ivr_migrations'))`. Так как каждый вызов `psql` — отдельная сессия, блокировку нужно брать **в том же вызове psql**, что и работа. Самый простой честный способ: собрать применение одной миграции в один вызов `psql` со скриптом на stdin, который делает `BEGIN; SELECT pg_advisory_xact_lock(...); <тело миграции>; INSERT INTO schema_migrations ...; COMMIT;`. Проверка «уже применена» тогда делается внутри той же транзакции — через `INSERT ... ON CONFLICT (version) DO NOTHING` и сравнение затронутых строк, либо повторным `SELECT` после взятия блокировки. Выбери подход сам, но в файле должно остаться комментарием, почему выбран именно он.
- Сохранить текущий вывод (`APPLY:`, `SKIP:`, `Done. Applied N migration(s).`) — на него смотрят проверки в планах 01–03.
