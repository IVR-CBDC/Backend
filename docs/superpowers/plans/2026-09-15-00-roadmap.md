## Перенесено из плана 04

- **05 (BFF/фронт):** список сервисов для `up` продублирован в `Makefile` и `ci.yml` — добавление bff/frontend надо делать в двух местах, расхождение не заметит ни один тест.
  `docker compose up --wait` считает готовым любой *running* контейнер без healthcheck, поэтому **новый сервис в compose обязан приносить healthcheck**, иначе e2e станут флейки.
  Цепочки `-f docker-compose.yml -f docker-compose.dev.yml` отключают автоподхват `docker-compose.override.yml` — оверлеи перечисляем явно (правило записано в README).
  Бюджет GHA-кэша 10 ГБ почти занят кэшем drogon: развести `scope:` для cpp-base и фронтовых сборок, иначе холодная сборка базы будет всплывать «случайно».
  В `ci.yml` нет `paths`-фильтров: PR, трогающий только фронт, гонит весь C++-пайплайн.
- **08 (k3s):** Traefik «наружу только bff и frontend» (спека §3) — отложено из плана 04, потому что этих сервисов ещё не было.
  `deploy.yml` копипастит `helm upgrade` по сервису; с пятью сервисами и внешними тегами из `frontend-tags.env` это надо переписать на матрицу.
- **Долг:** `infra/migrate.sh` буферизует вывод psql — долгая миграция в init-контейнере выглядит «молчащей», а `helm upgrade --wait --timeout 5m` при этом тикает; закрыть до первой тяжёлой миграции.
  Нет `lock_timeout`/`statement_timeout`: зависшая миграция держит advisory-lock, вторая реплика молча ждёт (в скрипте отмечено комментарием).
- **Вне кода (владелец репозитория):** включить обязательные проверки CI для ветки `main` — сейчас `deploy.yml` катит в k3s на каждый push в main, не дожидаясь `ci.yml`.

  рукопожатие WS будет отклоняться, а шапка покажет «Нет соединения». Заголовки кеширования настроены

  эскалировать, а не ставить в очередь (так родился дефект с истечением сессии); правило, сформулированное в
  спеке «для каждого экрана», нельзя закреплять за подмножеством экранов.

## Перенесено из плана 07 (вход в план 08)

**Требования, а не заметки:**
- **Маршрут к `/internal/emulator/tick` решить явно.** Весь детерминизм e2e стоит на `POST 127.0.0.1:18081/internal/emulator/tick`, который существует только потому, что dev-оверлей публикует порт. За Traefik такого пути нет (спека §4.3: наружу не публикуется), а NetworkPolicy, сужённая до bff/core, его активно заблокирует. Решить: e2e навсегда остаются на compose-стенде (тогда записать это в спеку) либо нужен тестовый путь (`kubectl port-forward` в джобе или маршрут на внутренний entrypoint). Обнаружить это посреди написания NetworkPolicy — самый дорогой порядок.
- **`ALLOWED_ORIGINS` обязан получить публичный адрес.** Фикстура шлёт `Origin: SPA_URL` на регистрацию вне браузера; если адрес не в списке, все тесты умрут на подготовке с `FORBIDDEN_ORIGIN`. А при отказе на апгрейде WS клиент не видит 4401 — индикатор вечно показывает «Подключение…», и в e2e это всплывёт немым таймаутом, а не внятной ошибкой.
- **`COOKIE_SECURE` параметризовать.** Сейчас прибито `false`; под https cookie нужен `Secure`, а `WsProvider` сам переключается на `wss:` по протоколу страницы.
- **Каждый новый сервис в compose обязан приносить healthcheck** (правило из плана 04) — иначе `--wait` возвращается рано и e2e становятся флаки.
- **Упрощение:** nginx фронта уже проксирует `/api` и `/ws` на BFF. Направив `E2E_BFF_URL` на `SPA_URL`, получаем один адрес вместо трёх, и `Origin` совпадает по построению. Тогда особым случаем остаётся только ручка tick.

**Долги, которые план 08 может закрыть по ходу:**
- `advance_sec` у `/internal/emulator/tick` (спека §4.3 приведена к реальности: возможности нет). Вместе с детерминированным рычагом отказа документа это убирает ~1.5% хвостовых таймаутов в `recovery.spec` и сокращает его с ~80 секунд до нескольких.
- Публиковать backend-образы в ghcr на `main` и тянуть теги в CI фронта: сейчас джоба e2e пересобирает C++ полностью на каждом PR (~25–40 минут на чистом раннере).
- Режим эмулятора сделать свойством набора файлов (`docker-compose.e2e.yml` с `EMULATOR_MANUAL: "true"`), а не соглашением в Makefile: за план 07 на эту ловушку наступили два агента. Плюс отдавать `emulator_manual` в `/health` и проверять в `global-setup`.
- Порядок мержа: ветка Backend обязана влиться раньше, чем CI фронта сможет пройти (джоба e2e зовёт `make e2e-stand-up`).

### Что осталось за пределами кода — действия владельца на GitHub

Ни одно из этих действий нельзя было выполнить здесь: у репозиториев нет доступного
remote, организации `IVR-CBDC` на GitHub не существует, CI-раннера нет.

1. **Включить обязательные проверки CI для `main`** в настройках репозитория.
   Сейчас `deploy.yml` катит в k3s на каждый push в `main`, не дожидаясь `ci.yml`.
2. **Заархивировать `IVR-CBDC/commission-service`** с README-ссылкой на Backend —
   история перенесена subtree в `services/service-commission`.
3. **Перед первым реальным выкатом прогнать ранбук** из README
   («Миграция k3s: test-python → commission»): установить `pg-commission`, снести
   устаревшие релизы `service-test-python` и `pg-test-python`.
4. **Первый выкат упрётся в два гварда — это ожидаемо, а не поломка:**
   - `infra/helm/frontend-tags.env` содержит `sha-3199330`, но образа с этим тегом в
     реестре нет и не будет, пока `publish.yml` фронт-репозитория не выполнится хоть раз;
     `docker manifest inspect` в `deploy.yml` честно скажет «образа нет в реестре».
   - Пароль БД: чарт сверяет его с Secret bitnami и обрывает выкат при расхождении.
     На стенде со старыми литеральными паролями (`auth`/`core`/`commission`) нужно
     либо `ALTER USER`, либо снос PVC — процедура описана в README.
   - Генерировать пароль `openssl rand -base64` нельзя: он даёт `/`, который гвард
     userinfo отвергает (пароль уезжает в DSN, а это URL).

### Что проверено рендером, а не выкатом

Кластера здесь не было. Всё k3s-шное (Helm, NetworkPolicy, Secret, порядок выката) и
весь CI/CD проверены `helm lint`/`helm template`, разбором YAML и воспроизведением
логики с заглушками вместо `helm`/`kubectl`/`docker`. Ни «задеплоено», ни «CI зелёный»
ни в одном отчёте не написано — и на защите это стоит формулировать так же прямо.
