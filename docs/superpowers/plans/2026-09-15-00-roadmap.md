# CBDC Hub — дорожная карта планов

Спека: `docs/superpowers/specs/2026-09-15-cbdc-hub-integration-design.md`

Спека покрывает несколько независимых подсистем, поэтому реализация разбита на отдельные планы.
Каждый план даёт рабочий, протестированный результат. Следующий план пишется после мержа
предыдущего — по реальным интерфейсам, а не по предположениям.

|---|---|---|---|---|

## Перенесено из плана 01 (учесть при написании следующих планов)

- **03 (core):** 401 `TOKEN_EXPIRED` от commission → 401, 5xx/таймаут → `503 UPSTREAM_UNAVAILABLE`; лимиты сценариев
  не зависят от валюты (cbdc доступен и не в RUB) — решить при описании правил сценариев; сохранять в
  `commission_breakdown` поля `subtotal`/`clamped`.
- **04 (compose/CI):** `migrate.sh` — `INSERT INTO schema_migrations` в той же транзакции + `pg_advisory_lock`,
  единая копия скрипта (сейчас дублируется в chart); CI для commission: `uv sync --locked && pytest` + db-тесты;
  предупреждения starlette/httpx в тестах (TestClient deprecation).
- **05 (BFF):** `docs/openapi/commission.yml` с requestBody/схемами ответов и security scheme (`HTTPBearer`).
- **03 (core), из плана 02:** вход в компанию по ИНН оставлен открытым как допущение демо
  (спека §3.2, README) — домен строится поверх этого осознанно; `company_id` берётся из атрибутов
  `common::JwtFilter`. Для изоляции пригодится Catch2-тест «токен компании A не видит данные B»
  на базе `testing_support::makeToken`.
- **08 (k3s):** отдельный liveness-путь без проверки БД; Secrets для паролей БД; NetworkPolicy сузить до bff/core.
- **Вне кода:** README-заглушка и архивирование `IVR-CBDC/commission-service` на GitHub (делает владелец);
  перед мержем в `main` — runbook из README («Миграция k3s: test-python → commission»).

## Перенесено из плана 03 (учесть при написании следующих планов)

- **04 (compose/CI):** `tests/api` (pytest, `make test-api`) заведён здесь (Task 6), но в CI его
  включает план 04 — сам план 03 только гоняет их вручную/локально, шага в CI нет.
- **04 (compose/CI):** `docker-compose.yml` пробрасывает `service-auth`/`service-core` на
  `127.0.0.1:18080`/`127.0.0.1:18081` специально для `tests/api`; план 04 решает, нужны ли эти
  порты после появления настоящего CI-стенда, или подключение должно идти как-то иначе
  (например, через сеть compose без публикации портов на хост).
  - Известное ограничение окружения в момент реализации: порт 8081 занят посторонним процессом
    на машине разработчика, из-за чего traefik иногда не поднимается — Task 6 обходит это,
    гоняя `tests/api`/`infra/smoke-deal.sh` напрямую на `ivr_backend-net`, а не через traefik;
    план 04 должен решить, актуально ли это для CI-раннера.
- **03 (core), из плана 02:** тест «токен компании A не видит данные B» на уровне Catch2 так и не
  написан (предполагался на базе `testing_support::makeToken`) — вместо него изоляция по
  `company_id` покрыта на уровне HTTP в `tests/api/test_core_deals.py`
  (`test_list_deals_is_isolated_by_company`, `test_get_foreign_deal_returns_404`).
- **Эмулятор, для авторов будущих тестов на этом домене:** исход одобрения документа —
  детерминированная функция `(deal_id, kind, attempt)` (обновлено финальным fix-wave-ом,
  см. F2 в `final-fixes.md`): `attempt 0` (первая подача) отклоняется как и раньше — хэш от
  `(deal_id, kind)`, ~10%; но `attempt >= 1` (любая переподача) одобряется всегда — переподача
  отклонённого документа никогда не блокируется снова, это и есть работающая история
  восстановления сделки. Тесты и `infra/smoke-deal.sh` предсказывают исход на стороне клиента
  (копия `fnv1a` в Python/bash) и подбирают `deal_id` под нужный сценарий, вместо того чтобы
  полагаться на шанс отказа/одобрения.
- **06 (SPA):** курсорная пагинация `/api/core/deals` (`?cursor=` → `next_cursor`) отложена —
  спека §4.5 (план 03) временно приведена в соответствие с реализацией (`?limit=` → `{items,
  count}`), на объёмах демо-дашборда курсоры не нужны. Добавить их, когда план 06 определит
  реальный размер страницы дашборда сделок.
