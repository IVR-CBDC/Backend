# CBDC Hub — дорожная карта планов

Спека: `docs/superpowers/specs/2026-09-15-cbdc-hub-integration-design.md`

Спека покрывает несколько независимых подсистем, поэтому реализация разбита на отдельные планы.
Каждый план даёт рабочий, протестированный результат. Следующий план пишется после мержа
предыдущего — по реальным интерфейсам, а не по предположениям.

## Перенесено из плана 01 (учесть при написании следующих планов)

- **03 (core):** 401 `TOKEN_EXPIRED` от commission → 401, 5xx/таймаут → `503 UPSTREAM_UNAVAILABLE`; лимиты сценариев
  не зависят от валюты (cbdc доступен и не в RUB) — решить при описании правил сценариев; сохранять в
  `commission_breakdown` поля `subtotal`/`clamped`.
- **04 (compose/CI):** `migrate.sh` — `INSERT INTO schema_migrations` в той же транзакции + `pg_advisory_lock`,
  единая копия скрипта (сейчас дублируется в chart); CI для commission: `uv sync --locked && pytest` + db-тесты;
  предупреждения starlette/httpx в тестах (TestClient deprecation).
- **05 (BFF):** `docs/openapi/commission.yml` с requestBody/схемами ответов и security scheme (`HTTPBearer`).
- **03 (core), из плана 02:** вход в компанию по ИНН оставлен открытым как допущение демо
  (спека §3.2, README) — домен строится поверх этого осознанно; `company_id` берётся из атрибутов
  `common::JwtFilter`. Для изоляции пригодится Catch2-тест «токен компании A не видит данные B»
  на базе `testing_support::makeToken`.
- **08 (k3s):** отдельный liveness-путь без проверки БД; Secrets для паролей БД; NetworkPolicy сузить до bff/core.
- **Вне кода:** README-заглушка и архивирование `IVR-CBDC/commission-service` на GitHub (делает владелец);
  перед мержем в `main` — runbook из README («Миграция k3s: test-python → commission»).

## Перенесено из плана 03 (учесть при написании следующих планов)

- **04 (compose/CI):** `tests/api` (pytest, `make test-api`) заведён здесь (Task 6), но в CI его
  включает план 04 — сам план 03 только гоняет их вручную/локально, шага в CI нет.
- **04 (compose/CI):** `docker-compose.yml` пробрасывает `service-auth`/`service-core` на
  `127.0.0.1:18080`/`127.0.0.1:18081` специально для `tests/api`; план 04 решает, нужны ли эти
  порты после появления настоящего CI-стенда, или подключение должно идти как-то иначе
  (например, через сеть compose без публикации портов на хост).
  - Известное ограничение окружения в момент реализации: порт 8081 занят посторонним процессом
    на машине разработчика, из-за чего traefik иногда не поднимается — Task 6 обходит это,
    гоняя `tests/api`/`infra/smoke-deal.sh` напрямую на `ivr_backend-net`, а не через traefik;
    план 04 должен решить, актуально ли это для CI-раннера.
- **03 (core), из плана 02:** тест «токен компании A не видит данные B» на уровне Catch2 так и не
  написан (предполагался на базе `testing_support::makeToken`) — вместо него изоляция по
  `company_id` покрыта на уровне HTTP в `tests/api/test_core_deals.py`
  (`test_list_deals_is_isolated_by_company`, `test_get_foreign_deal_returns_404`).
- **Эмулятор, для авторов будущих тестов на этом домене:** исход одобрения документа —
  детерминированная функция `(deal_id, kind, attempt)` (обновлено финальным fix-wave-ом,
  см. F2 в `final-fixes.md`): `attempt 0` (первая подача) отклоняется как и раньше — хэш от
  `(deal_id, kind)`, ~10%; но `attempt >= 1` (любая переподача) одобряется всегда — переподача
  отклонённого документа никогда не блокируется снова, это и есть работающая история
  восстановления сделки. Тесты и `infra/smoke-deal.sh` предсказывают исход на стороне клиента
  (копия `fnv1a` в Python/bash) и подбирают `deal_id` под нужный сценарий, вместо того чтобы
  полагаться на шанс отказа/одобрения.
- **06 (SPA):** курсорная пагинация `/api/core/deals` (`?cursor=` → `next_cursor`) отложена —
  спека §4.5 (план 03) временно приведена в соответствие с реализацией (`?limit=` → `{items,
  count}`), на объёмах демо-дашборда курсоры не нужны. Добавить их, когда план 06 определит
  реальный размер страницы дашборда сделок.

## Перенесено из плана 03

- **04 (compose/CI):** `tests/api` заведён в плане 03 и гоняется целью `make test-api` — включить в CI; у `service-core`
  и `service-auth` нет compose-healthcheck (есть только у commission), из-за чего готовность стенда проверяет
  `conftest.stack_ready`; порты 18080/18081 и 5433–5435 проброшены безусловно, а не под профилем.
- **05 (BFF):** живой тест подписки на `deal-events:{company_id}` — сейчас факт публикации доказан косвенно
  (`published_at` ставится только после успешного `PUBLISH`), приём сообщения подписчиком не проверен; BFF и так
  станет настоящим потребителем, там тест будет честным. **Дедупликация только по множеству увиденных `seq`,
  никогда не по «отбрасывать всё, что меньше последнего»** — порядок не гарантирован (спека §4.4). Redis pub/sub
  не хранит историю: при переподключении BFF обязан перезапросить список сделок, а не ждать догоняющих событий.
- **06 (SPA):** курсорная пагинация списка сделок (`?cursor=`, `next_cursor`) — спека §4.5 приведена к текущей
  реализации (`?limit=` → `{items, count}`), курсор добавляем, когда UX дашборда задаст размер страницы.
- **Долг по структуре:** `services/service-core/src/repository.cc` (443 строки) и `emulator.cc` (357) переросли
  ориентир в ~300 строк; шов для repository.cc известен — сериализация (`dealSummaryJson`/`dealJson`/
  `progressPercentForStage` → `deal_json.cc`), не `create`/`apply`.

## Перенесено из плана 04

- **05 (BFF/фронт):** список сервисов для `up` продублирован в `Makefile` и `ci.yml` — добавление bff/frontend надо делать в двух местах, расхождение не заметит ни один тест.
  `docker compose up --wait` считает готовым любой *running* контейнер без healthcheck, поэтому **новый сервис в compose обязан приносить healthcheck**, иначе e2e станут флейки.
  Цепочки `-f docker-compose.yml -f docker-compose.dev.yml` отключают автоподхват `docker-compose.override.yml` — оверлеи перечисляем явно (правило записано в README).
  Бюджет GHA-кэша 10 ГБ почти занят кэшем drogon: развести `scope:` для cpp-base и фронтовых сборок, иначе холодная сборка базы будет всплывать «случайно».
  В `ci.yml` нет `paths`-фильтров: PR, трогающий только фронт, гонит весь C++-пайплайн.
- **08 (k3s):** Traefik «наружу только bff и frontend» (спека §3) — отложено из плана 04, потому что этих сервисов ещё не было.
  `deploy.yml` копипастит `helm upgrade` по сервису; с пятью сервисами и внешними тегами из `frontend-tags.env` это надо переписать на матрицу.
- **Долг:** `infra/migrate.sh` буферизует вывод psql — долгая миграция в init-контейнере выглядит «молчащей», а `helm upgrade --wait --timeout 5m` при этом тикает; закрыть до первой тяжёлой миграции.
  Нет `lock_timeout`/`statement_timeout`: зависшая миграция держит advisory-lock, вторая реплика молча ждёт (в скрипте отмечено комментарием).
- **Вне кода (владелец репозитория):** включить обязательные проверки CI для ветки `main` — сейчас `deploy.yml` катит в k3s на каждый push в main, не дожидаясь `ci.yml`.

## Перенесено из плана 05

- **06 (SPA):** контракт для SPA описан в README Frontend-репозитория (раздел «Контракт для SPA»): формы кадров WS,
  словарь кодов ошибок, смысл `4401`, и правило **«на каждый `connection.ack`, включая переподключения,
  перезапрашивай текущий экран»** — у Redis pub/sub нет истории, дыру после реконнекта SPA иначе не заметит.
  BFF в разработке слушает `127.0.0.1:14000`. `frontend/pnpm-workspace.yaml` удалён в плане 05 и понадобится
  снова: Vite тянет esbuild так же, как vitest.
- **07 (e2e):** стенд готов ждать по `/ready` (готовность = живой подписчик Redis + достижимость upstream'ов,
  кеш 2s); `/health` — только живость процесса.
- **08 (k3s):** `readinessProbe` → `/ready`, `livenessProbe` → `/health`. Traefik: наружу только bff и frontend
  (перенесено ещё из плана 04). Переименовать ручку auth `/.well-known/jwks.json` — она отдаёт PEM, а
  content-type `application/x-pem-file`; после переименования из BFF можно убрать двойной разбор.
  **Если `SameSite` у cookie когда-нибудь ослабят (поддомены, возвратные потоки) — перепроверить защиту WS:**
  сейчас чужой Origin отклоняется до рукопожатия, и это единственный долгоживущий канал.
  Образ BFF публикует CI Frontend-репозитория (`ghcr.io/ivr-cbdc/frontend/bff`), тег приезжает в
  `infra/helm/frontend-tags.env`; в compose сервис `bff` пока под профилем `bff`, потому что образ не опубликован.
- **CI:** `bff` не добавлен в джобу `api` бэкенда — у Frontend-репозитория ещё нет remote и образа в ghcr;
  подключить, когда появятся (отмечено в README бэкенда).
